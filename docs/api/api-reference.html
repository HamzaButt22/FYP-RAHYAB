Pseudonymous accounts, consent, telemetry, scoring, library, sharing, dashboard and admin for Rahyaab.

Contract for the Rahyaab backend (FastAPI). It is the source of truth for client code generation (packages/shared-ts) and for contract tests.

  • All paths are under /v1. Breaking changes need a new major version (see docs/api/README.md).
  • Errors use RFC 9457 application/problem+json.
  • List endpoints use cursor pagination (cursor, limit ≤ 100).
  • Every request may send X-Request-Id; the server echoes it.
  • Student data is pseudonymous. No endpoint accepts a student's name, phone, email or photo.
  • CORS: only the dashboard origin is allowed (exact allowlist, credentials on); the app and parent pages need none (SECURITY.md §5.1).
  • Access rule: a wrong role gets 403; an object of another tenant (school, class or student) gets 404, so its existence is not revealed.
  • Parent pages (/p, /c) are authorised by the 128-bit capability token in the path; it is never sent in a query string.

auth

Student join, token refresh, staff login with MFA

Join a class with a code and create a pseudonymous profile

Rate limits (NFR-67), counted in PostgreSQL so all workers agree: 10 attempts per 15 minutes per device, 30 failed attempts per hour per class code (then the code is paused and the teacher is told), and a high per-IP ceiling of 300 per 15 minutes, because a whole class on school Wi-Fi or a mobile network (CGNAT) shares one IP. A bad format gets 422 with a format hint; an unknown, expired or paused code gets the same generic 404 message and similar timing. An optional claim_code binds a signed paper consent slip to the new profile (FR-05a).

telemetry

Idempotent event batches (RFC-0002)

Upload up to 500 events (gzip, ≤ 1 MB); idempotent per event

Requires valid parental consent (NFR-45). The envelope is validated loosely (an array of objects) so one bad event never fails the batch; each event is then validated on its own against Event. Valid events are stored append-only. Final failures are quarantined and listed in rejected. Order-dependent failures (the run is not known yet, or a sequence gap) are listed in deferred: the app keeps them and retries after the earlier events arrive (RFC-0002).
